# 日本語ビジネス文書タスクにおけるLLM量子化方式の比較評価
## GGUF Q4_K_M と AWQ INT4 の速度・品質・メモリ効率

**A Comparative Evaluation of LLM Quantization Formats for Japanese Business Document Tasks:
Speed, Quality, and Memory Efficiency of GGUF Q4_K_M vs AWQ INT4**

---

著者：大橋 功  
所属：株式会社喋ラボ  
公開日：2026年6月

---

## Abstract

本稿では、NVIDIA RTX 4060 Laptop（VRAM 8GB）という制約されたGPU環境において、オープンソースLLMの量子化方式（GGUF Q4_K_M および AWQ INT4）が日本語ビジネス文書タスクの速度・品質・メモリ使用量に与える影響を実測により評価した。対象タスクは、架空の日本語会議録を用いた（1）要約生成と（2）アクションアイテムのJSON構造化抽出の2種類とし、コンテキスト長（8K / 16K / 32K トークン）を変数として系統的に測定した。

評価対象モデルはQwen3-8B および Gemma4-E4B の2モデルで、いずれもGGUF Q4_K_M フォーマットで全条件（計24試行）を完走した。AWQ INT4（vLLM ランタイム）については、重み5.71GiBに加えvLLMのオーバーヘッドによりKVキャッシュ確保が最大0.73GiBに限られ、最小実験条件（8Kコンテキスト）を含む全条件で起動不可であることを定量的に示した。

主要な発見として、（1）GGUF Q4_K_M においてJSON有効率は全モデル・全コンテキストで100%を達成し、（2）抽出品質（F1スコア）はコンテキスト長に依存せずモデル間で大きく異なり（Qwen3-8B: 0.61 vs Gemma4-E4B: 0.25〜0.37）、（3）速度劣化はQwen3-8BでGPUオフロードにより32Kで8.0 tok/sまで低下する一方、Gemma4-E4BはMoEアーキテクチャのKVキャッシュ効率により32Kでも35.8 tok/sを維持することを確認した。これらの結果は、8GB VRAM環境における実務的な量子化方式選択に具体的な指針を提供する。

## 1. はじめに

ローカル環境でのLLM実行に対する需要が急速に高まっている。プライバシー保護、レイテンシ削減、クラウドAPIコストの回避といった実務的要件から、企業が自社インフラ上でオープンソースLLMを運用するケースが増えている。

このような文脈において量子化技術は不可欠である。FP16フルプレシジョンの7〜8Bモデルは約14GBのVRAMを要するが、4ビット量子化によりコンシューマーGPUでも動作可能な3〜6GB程度まで圧縮できる。

現在主流の量子化フォーマットには、汎用性の高いGGUF（llama.cppエコシステム）とNVIDIA GPU向けに最適化されたAWQ INT4がある。しかし既存の比較研究の多くは英語の汎用ベンチマーク（MMLU、HumanEvalなど）を用いており、以下の問いに答えていない。

**「日本語のビジネス文書処理という実務タスクにおいて、これらの量子化方式はどのような差異を示すか。特にVRAM 8GBという制約環境では何が現実的に動作するのか。」**

本稿はこの問いに実験的に回答するものである。

### 1.1 本稿の主な貢献

- 日本語会議録を用いた要約・JSON抽出タスクでの量子化比較（既存研究との差別化）
- コンテキスト長（8K/16K/32K）を変数としたGPUオフロード挙動の定量化
- AWQ INT4 + vLLMが8GB VRAM環境において最小実験条件すら起動不可であることの実測検証
- 実務者向けの量子化選択指針の提示

## 2. 背景と関連研究

### 2.1 量子化の基礎

LLMの重みはFP16（16ビット浮動小数点）で表現されると1パラメータあたり2バイトを要する。7〜8Bモデルのフルプレシジョン保存には約14GBが必要であり、VRAM 8GBのコンシューマーGPUには収まらない。

量子化とは重みの数値表現を低ビット精度に変換する技術である。4ビット整数（INT4）への変換では、モデルサイズを約1/4に圧縮できる。品質劣化との関係はモデルサイズと量子化方式に依存するが、一般にQ4_K_Mで約92%、AWQ INT4で約95%の品質保持率が報告されている。

### 2.2 GGUF Q4_K_M

GGUFはllama.cppプロジェクトが開発した量子化フォーマットで、CPU・GPU・Apple Silicon のいずれでも動作する汎用性が特徴である。K-Quant（Q4_K_M）は重みをブロック単位で量子化し、重要な層（embedding層など）を混合精度で保持する。Mバリアントは「Medium」を意味し、全体的なバランスが良い設定として広く普及している。OllamaやLM Studioなど主要なローカルLLMツールがこのフォーマットをサポートしている。

VRAMが不足する場合、llama.cppはGPUに乗らない層をCPUメインメモリにオフロードするハイブリッド実行が可能である。ただしCPU↔GPU間のPCIeバス転送がボトルネックとなり、オフロード層が増えると速度が著しく低下する。

### 2.3 AWQ INT4

AWQ（Activation-aware Weight Quantization）は、実際のデータをモデルに通して各重みの出力への寄与（活性化の大きさ）を事前計測し、重要な重みを高精度で保持しつつそれ以外を積極的に圧縮する手法である。理論的にはGGUFより品質劣化が少ない。NVIDIA GPU向けの行列演算カーネルに最適化されており、推論スループットが高い。vLLM や TGI などの高スループット推論サーバーで広く採用されている。

一方でAWQの実行にはNVIDIA CUDAが必須であり、またvLLMはKVキャッシュをGPUメモリにあらかじめ確保する設計上、VRAM消費が大きい。

### 2.4 コンテキスト長とKVキャッシュ

Transformer系モデルはAttention計算のためKVキャッシュをGPUメモリに保持する。KVキャッシュのサイズはコンテキスト長に比例して増大する。8Bクラスのモデルでは、8Kコンテキストで約1.1GiB、16Kで約2.25GiB、32Kで約4.5GiBのVRAMをKVキャッシュが占有する。VRAM 8GB環境では、このKVキャッシュとモデル重みの競合が実験設計上の重要な変数となる。

## 3. 実験設計

### 3.1 ハードウェア

本実験はすべて以下の単一マシンで実施した。

| 項目 | 仕様 |
|------|------|
| GPU | NVIDIA RTX 4060 Laptop GPU |
| VRAM | 8GB（8,188 MiB） |
| CUDA | 12.8 |
| ドライバ | 580系 |
| OS | Ubuntu Linux |
| ランタイム | llama-cpp-python 0.3.26（CUDA cu124）/ vLLM 0.22.1 |

### 3.2 評価モデル

| モデル | パラメータ数 | アーキテクチャ | 重みサイズ（Q4_K_M） |
|--------|-------------|----------------|----------------------|
| Qwen3-8B | 8B（Dense） | 36層 | 約5.0GB |
| Gemma4-E4B | 4B Effective（MoE） | 42層 | 約5.4GB |

Qwen3-8BはAlibabaが開発した8Bデンスモデルで、日本語性能が高いことで知られる（Shisa評価: 8.08/10）。Gemma4-E4BはGoogleが開発したMixture-of-Experts（MoE）モデルで、推論時に活性化するパラメータは約4B相当であり、KVキャッシュが小さい。両モデルはApache 2.0ライセンスで商用利用可能である。

### 3.3 タスク設計

#### タスクA：日本語会議録の要約

架空の日本語会議トランスクリプトを入力として200〜300字程度の要約文を生成させた。

```
以下は会議のトランスクリプトです。
会議の要点を200〜300字で要約してください。

## トランスクリプト
{transcript}

## 要約
```

#### タスクB：アクションアイテムのJSON構造化抽出

同じトランスクリプトから、担当者・タスク・期日・優先度を含む構造化JSONを出力させた。

```
以下の会議トランスクリプトから、アクションアイテムを抽出してください。
必ず以下のJSONスキーマに従って出力してください。
それ以外のテキストは出力しないでください。

スキーマ：
{
  "action_items": [
    {
      "task": "タスクの内容（文字列）",
      "assignee": "担当者名（不明な場合はnull）",
      "due_date": "YYYY-MM-DD形式（不明な場合はnull）",
      "priority": "high/medium/low のいずれか"
    }
  ]
}
```

両タスクともInstruct用チャットテンプレートを適用し、Qwen3のthinking modeはオフに設定した。

### 3.4 テストデータ

架空の日本語会議録を3種類用意した。実際の会議録は一切使用していない。

| データID | 会議種別 | トークン数 | コンテキスト条件 |
|----------|----------|-----------|-----------------|
| T1 | 週次進捗MTG | 2,591 | 8K・16K・32K |
| T2 | 月次レビュー | 6,515 | 16K・32K |
| T3 | 四半期計画MTG | 12,681 | 32Kのみ |

テストデータには担当者・期日が明確なアクションアイテムと曖昧なもの（due_date: null）を意図的に混在させた。

### 3.5 実験条件マトリクス

| モデル | 量子化 | 8K | 16K | 32K | 試行数 |
|--------|--------|----|-----|-----|--------|
| Qwen3-8B | GGUF Q4_K_M | ✓ | ✓ | ✓ | 12 |
| Gemma4-E4B | GGUF Q4_K_M | ✓ | ✓ | ✓ | 12 |
| Qwen3-8B | AWQ INT4 | — | — | — | 3（全ERROR） |

コンテキスト長は `--ctx-size` パラメータで明示的に指定した。

### 3.6 測定指標

**速度・メモリ系**

| 指標 | 定義 |
|------|------|
| 生成速度（tok/s） | 生成フェーズの平均トークン/秒 |
| TTFT（秒） | 入力受付から最初のトークン出力までの時間 |
| ピークVRAM（GB） | 推論中のpynvml実測最大値 |
| オフロード層数 | GPUに乗せた層数 / 全層数 |

**品質系**

| 指標 | タスク | 定義 |
|------|--------|------|
| JSON有効率 | タスクB | json.loads()でパース成功した割合 |
| アクションアイテムF1 | タスクB | taskフィールドの部分一致によるF1スコア |
| assignee精度 | タスクB | 担当者フィールドの一致率 |
| due_date精度 | タスクB | 期日フィールドの一致率 |

## 4. 実験結果

### 4.1 GGUF Q4_K_M：速度・メモリ測定結果

#### Qwen3-8B（Q4_K_M）

| コンテキスト | tok/s | TTFT（秒） | ピークVRAM | GPUオフロード |
|-------------|-------|-----------|------------|---------------|
| 8K | **28.6** | 2.5 | 6.62 GB | 36/36層（全層） |
| 16K | 21.7 | 6.3 | 7.69 GB | 33/36層（部分） |
| 32K | 8.0 | 18.4 | 7.46 GB | 18/36層（部分） |

8Kではモデルの全36層をGPUに載せることができ、28.6 tok/sを実現した。16Kに移ると、KVキャッシュの増大によりGPUメモリが逼迫し3層をCPUにオフロードする必要が生じ、速度が21.7 tok/sに低下した。32Kでは半数以上の18層がCPUオフロードとなり、PCIeバス転送がボトルネックとなって速度は8.0 tok/sまで低下した。TTFTも2.5秒から18.4秒へと7倍以上に増加した。

#### Gemma4-E4B（Q4_K_M）

| コンテキスト | tok/s | TTFT（秒） | ピークVRAM | GPUオフロード |
|-------------|-------|-----------|------------|---------------|
| 8K | **41.0** | 1.3 | 4.50 GB | 42/42層（全層） |
| 16K | 38.5 | 2.4 | 5.11 GB | 42/42層（全層） |
| 32K | 35.8 | 4.2 | 6.49 GB | 42/42層（全層） |

Gemma4-E4BはMoEアーキテクチャの特性によりKVキャッシュが小さく、32Kコンテキストにおいても全42層をGPUに載せることができた。その結果、速度は8K（41.0 tok/s）から32K（35.8 tok/s）で13%しか低下せず、TTFTも4.2秒に留まった。

### 4.2 AWQ INT4：起動不可の定量記録

Qwen3-8B-AWQモデル（Qwen/Qwen3-8B-AWQ、4bit重みで5.71GiB）をvLLM 0.22.1で起動しようとした結果、全ての実験条件で起動に失敗した。

vLLMは起動時に `gpu_memory_utilization` 比率分のVRAMをKVキャッシュとして事前確保する。VRAM 8GBに対してAWQモデル重みが5.71GiB（69.7%）を占有するため、残余のKVキャッシュが実験コンテキスト長に必要なサイズに達しない。

#### KVキャッシュ確保量スイープ（max_model_len=8192固定）

| gpu_memory_utilization | KV確保量 | 推定最大コンテキスト | 8K起動 |
|------------------------|---------|---------------------|--------|
| 0.90 | 0.19 GiB | 1,392 トークン | ✗ |
| 0.93 | 0.42 GiB | 3,056 トークン | ✗ |
| 0.95 | 0.57 GiB | 4,160 トークン | ✗ |
| 0.97 | 0.73 GiB | 5,280 トークン | ✗ |

8Kコンテキストには1.12GiBのKVキャッシュが必要であるが、利用率を上限の0.97まで引き上げても確保できたのは0.73GiBに過ぎず、起動は失敗した。

なお、AWQ自体のソフトウェア的な問題ではないことを確認するため、縮小条件（ctx=4096、util=0.97）で検証したところ、起動成功・推論完了（22.67 tok/s、有効JSON出力）を確認した。8GB VRAMにおけるAWQ INT4の動作限界は純粋にハードウェアのメモリ容量によるものである。

### 4.3 品質比較：JSON抽出タスク

#### JSON有効率

全GGUF試行（24試行）においてJSON有効率は**100%**であった。これはチャットテンプレートの適切な適用とInstruct系モデルの構造化出力能力によるものと考えられる。

#### アクションアイテム抽出F1スコア

| モデル | 8K | 16K | 32K | 平均 |
|--------|-----|-----|-----|------|
| Qwen3-8B | 0.615 | 0.612 | 0.619 | **0.615** |
| Gemma4-E4B | 0.250 | 0.365 | 0.343 | **0.319** |

Qwen3-8BはF1スコア0.61〜0.62と安定して高品質な抽出を行った。特筆すべきは、コンテキスト長が変化してもF1スコアがほぼ一定（0.612〜0.619の範囲）であることで、速度劣化とは独立して品質が安定している。

Gemma4-E4BはF1スコアが0.25〜0.37と低く、Qwen3-8Bの約半分の水準に留まった。フィールド別精度を確認すると、assignee（担当者）・due_date（期日）・priority（優先度）の各フィールド精度は全て1.0であった。つまりGemma4-E4Bは個々のフィールド抽出は正確だが、アクションアイテム自体の網羅的な列挙（Recall）が低いことがF1低下の主因である。

### 4.4 速度・品質トレードオフの全体像

| モデル | 量子化 | 8K tok/s | 32K tok/s | 平均F1 | 32KでのVRAM |
|--------|--------|----------|-----------|--------|-------------|
| Qwen3-8B | GGUF Q4_K_M | 28.6 | 8.0 | 0.615 | 7.46GB |
| Gemma4-E4B | GGUF Q4_K_M | 41.0 | 35.8 | 0.319 | 6.49GB |
| Qwen3-8B | AWQ INT4 | — | — | — | 起動不可 |

Gemma4-E4BはQwen3-8Bの1.4〜4.5倍速く動作し、VRAM消費も少ない。一方で抽出品質はQwen3-8Bの約半分である。速度優先のユースケース（速報要約、リアルタイム処理）ではGemma4-E4Bが有利であり、品質優先のユースケース（重要会議の議事録、アクションアイテム管理）ではQwen3-8Bが適切である。

## 5. 考察

### 5.1 「AWQはGGUFより高品質」という通説の検証

量子化方式の比較においてAWQはGGUFより品質保持率が高い（AWQ 95% vs GGUF Q4_K_M 92%）と広く言われている。しかし本実験が示したのは、VRAM 8GBという制約環境ではAWQの品質優位性を発揮する以前に、そもそも実用的なコンテキスト長での起動が不可能だということである。

このことは「量子化方式の選択はモデル品質だけでなく、ランタイムとハードウェアの組み合わせを含めたシステムレベルで評価すべき」という重要な示唆を持つ。

### 5.2 コンテキスト長の影響

Qwen3-8BにおいてGPUオフロードの増加に伴う速度劣化が顕著であった（8K: 28.6 → 32K: 8.0 tok/s、3.6倍の差）。一方でF1スコアには有意な変化がなかった（0.612〜0.619）。

これは実務上重要な発見である。**コンテキスト長の変化は品質に影響せず、速度とメモリにのみ影響する。** 長い会議録でも品質を維持できるが、32Kを扱うには速度コストを受け入れる必要がある。

### 5.3 モデルアーキテクチャとVRAM挙動

GemmaのMoEアーキテクチャが示したVRAM効率の高さ（32Kで全層GPUが可能）は、「パラメータ総数よりも活性化パラメータ数と注意機構の設計がVRAM消費を決定する」ことを示している。単純なパラメータ数で必要VRAMを見積もることの危険性がここに表れている。

### 5.4 Gemma4-E4Bの低F1の解釈

Gemma4-E4BのF1が低い原因は品質の低さではなく、アクションアイテムの抽出網羅性（Recall）の低さにある。フィールドレベルの精度は100%であり、抽出できた項目については正確である。これは「少ないが確実な抽出」対「多いが精度が高い抽出」というトレードオフとして解釈でき、精度重視のユースケースではGemma4-E4Bが適する可能性もある。

### 5.5 実務的な選択指針

```
【VRAM 8GBでの量子化方式選択フロー】

コンテキスト長 < 16K かつ 速度優先？
  → Gemma4-E4B GGUF Q4_K_M（41 tok/s、4.5GB）

品質が重要かつ コンテキスト長 ≤ 8K？
  → Qwen3-8B GGUF Q4_K_M（28.6 tok/s、6.6GB）

長いコンテキスト（16〜32K）が必要かつ品質重視？
  → Qwen3-8B GGUF Q4_K_M（速度低下を許容）

AWQ INT4（vLLM）を使いたい？
  → VRAM 16GB以上が必要（8GBでは実用不可）
```

## 6. 限界と今後の課題

本研究にはいくつかの限界がある。

**評価データの制約**：テストデータは架空の会議録であり、実際の業務会議録での性能を保証するものではない。アクションアイテムのF1スコアはグランドトゥルースとの部分一致で算出しており、意味的に同等でも表現が異なる場合に過小評価される可能性がある。

**モデルのカバレッジ**：本実験はQwen3-8BとGemma4-E4Bの2モデルに限定した。他のモデル（Llama3-8B、Phi-4-miniなど）では異なる結果が得られる可能性がある。

**ランタイムの限定**：AWQ評価にvLLM 0.22.1を使用したが、他のAWQ対応ランタイム（ExLlamaV2など）では異なるメモリ効率を示す可能性がある。

**今後の課題**：Mac mini（64GB統合メモリ）環境でのMLX 4bitとGGUF Q4_K_Mの比較、特に32B・MoEクラスモデルの評価を次フェーズとして計画している。また、ROUGE-LおよびLLM-as-judgeによる要約品質の定量評価も今後の課題である。

## 7. まとめ

本稿では、VRAM 8GBのGPU環境において日本語ビジネス文書タスクでの量子化方式比較を実施した。主要な知見を以下に整理する。

1. **AWQ INT4は8GB VRAMでは実用不可**: vLLM使用時、モデル重み5.71GiBによりKVキャッシュが最小実験条件（8Kコンテキスト）にも不足し、全条件で起動失敗。縮小条件（4K）では正常動作し、問題は純粋なメモリ容量によるものと確認した。

2. **GGUF Q4_K_M は全条件で完走、JSON有効率100%**: 24試行すべてが正常完了し、JSON構造化出力の安定性は高い。

3. **速度劣化はコンテキスト長依存、品質劣化はモデル依存**: Qwen3-8Bは32Kで速度が8.0 tok/sまで低下するがF1は安定（0.61）。Gemma4-E4Bは32Kでも35.8 tok/sを維持するがF1は0.32に留まる。

4. **アーキテクチャがVRAM挙動を決定する**: GemmaのMoE構造はKVキャッシュを削減し、32KでもVRAM 6.5GBで全層GPU実行が可能。Qwenはコンテキスト増大とともに部分オフロードを強いられる。

これらの結果は、「VRAM 8GBでAWQを使えば精度が上がる」という通説が実際には成り立たないことを示しており、制約環境での実装判断に有用な実証的根拠を提供する。
